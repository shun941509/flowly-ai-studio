# Flowly 통합 기능 명세 · 예제 프로젝트 플랫폼

2026-10-23 갱신. 이 문서는 기존 제품·노드·실행·공유 요구와 예제 카탈로그 계획을 합친 구현 기준이다. 상세 런타임 계약은 `FEATURE_SPEC.md`, `NODE_V4_CONTRACT.md`, `NODE_V5_CONTRACT.md`, 카탈로그 API는 `EXAMPLE_CATALOG_CONTRACT.md`를 따른다. 완료 판정은 코드와 검증 기록에 한한다.

기존 3,200개 완료 보고는 자연어 계약을 실행 워크플로로 잘못 집계한 것으로 철회했다. 구조 재검사 결과와 현재 기준은 [카탈로그 계약](EXAMPLE_CATALOG_CONTRACT.md)을 따른다.

## 1. 제품 경계

일반 사용자는 한국어 웹에서 로그인해 워크플로와 자료를 설계·관리·공유하고 실행 프로젝트를 내려받는다. 웹은 OpenAI를 호출하지 않는다. 미리보기는 미리보기로 표시한다. 실제 모델·서비스 호출은 사용자가 키를 설정한 Node.js/Python 프로젝트에서만 한다.

웹에는 모델 키 입력·전달·저장을 추가하지 않는다. 내보낸 `.env.example`은 빈 설정 이름과 예시만 가진다. `.env`는 사용자의 로컬 편집기로 작성하고 Git에서 제외한다. 키를 채팅, 워크플로 JSON, 자료, URL, 로그에 넣지 않는다. 환경에 이미 있는 키를 개발자가 몰래 재사용하지 않는다.

## 3. 노드와 설정 구분

기존 28개 노드는 유지한다. 입력/양식/파일/자동 시작, 자료/지침, AI 답변/Agent, 도구, 조건/분류, 변환/병합, 검색, 병렬/팀/작업 조정/하위 흐름/반복, 사람 검토, 기억, 오류, 문서 처리, 필터, 평가, 파일 출력, 답변 출력, 보상 작업이다.

- Agent·AI 답변: 도구 사용 여부와 반복 책임이 달라 별도 노드다.
- 병렬·에이전트 팀·작업 조정: 독립 병렬, 정해진 역할, 모델의 허용 작업 선택이 각각 다르므로 별도 노드다.
- RAG는 단일 불투명 노드가 아니라 자료 검색→근거 전달→답변→평가의 조합이다. 검색 방식·topK·청크 크기는 검색 노드 설정이다.
- 모델·온도·토큰/시간 한도·도구 허용 목록·재시도·승인·출력 스키마는 기존 노드/실행 정책 설정이다.
- LangGraph·CrewAI 같은 SDK 이름은 노드가 아니라 구현 변형/내보내기 대상이다.
- 하네스는 체크포인트·평가·예산·취소·복구 등 실행 관리 계층이다. 단순히 '하네스' 노드를 추가해 완료라고 표시하지 않는다.
- GraphRAG·샌드박스 코드·브라우저·음성은 실제 어댑터와 상태 계약이 구현된 후 노드/설정 경계를 결정한다.

## 5. 3,200개 확장 규칙

이전 3,200개 자연어 업무 계약은 저장소의 JSON 아카이브로 보존한다. 실행 구조를 개별 설계한 항목만 공개하고, 재설계 대기 원본은 예제 화면·검색·상세·복제·다운로드 API에서 제공하지 않는다. 새 독립 업무도 추가되므로 아카이브의 미전환 건수와 3,200개 목표까지 남은 구현 수는 서로 다를 수 있다. 현재 구현·검증·남은 수는 [집계](EXAMPLE_CATALOG_INVENTORY.md)를 따른다. 사례 탭은 제거하며 인증된 `GET /api/examples?view=cases`는 410, 공개 설계에 없는 기존 사례 ID의 상세·복제·직접 ZIP 요청은 404로 응답한다. 이미 사용자가 만든 워크플로와 자료 사본은 유지한다. 3,200개 구현 목표는 미완료다.

새 실행 원본은 `domain/workflow-designs/`에 작성한다. 제목·문서·프롬프트·좌표·프레임워크 변경이나 같은 구조의 설정 교체로 수를 늘리지 않는다. 불필요한 노드·변환·분기·중첩을 삽입해 구조 서명만 바꾸는 것도 금지한다. 입력 형식, 단계별 데이터 전달, 분기, 반복, 조정, 검토·복구에서 업무에 필요한 제어와 데이터 처리 차이를 설계하고, 그 차이를 정상·경계 시나리오의 실제 경로·결과·상태로 입증해야 한다. 구조 검사와 별도로 각 노드가 해당 동작에 기여하는지 검토한다.

`pnpm workflow:build`와 `pnpm catalog:audit`는 구조와 실행 설정의 중복을 각각 검사한다. 같은 구조에서 설정만 바꾼 항목도 독립 설계로 집계하지 않는다. `pnpm test:examples`는 새 그래프의 실제 두 언어 CLI 시나리오를 검사하며 증거는 `examples/workflow-verification.json`이다. `pnpm catalog:complete`는 현재 설계·실행기·시나리오·ZIP 해시와 목표 수를 대조한다. 부분 집계는 `incomplete`로 기록하며 목표 미달 시 종료 코드 1을 반환한다. 기존 검토·검증 파일을 새 그래프의 증거로 승계하지 않는다.

## 6. 보안·복구·검증 기준

예제는 외부 쓰기를 기본 허용하지 않는다. 허용 도구는 사용자 연결과 현재 권한을 검사한다. 외부 변경 예제를 추가할 때는 승인 객체를 실행·도구·인자 해시·사용자·만료에 묶고 재개 시 재검사한다. 알 수 없는 쓰기 결과를 자동 재시도하지 않는다. 현재 구현의 durable 체크포인트/멱등성 원장을 재사용한다.

검증의 의미:
1. 구조: 스키마·DAG·입력 매핑·자료 참조 검사.
2. Node/Python 로컬: 실제 ZIP을 풀어 CLI 설정 검사를 수행하고, 명시적 테스트 어댑터로 그래프·입출력·사람 검토를 실행. 모델의 업무 정답 검증이 아님.
3. SDK 오프라인: 실제 설치 SDK에 테스트 모델을 주입해 도구·출력·루프를 검증. 외부 API 호출이 아님.
4. 실제 연결: 사용자의 로컬 키와 서비스로 실행 후 호출/비용/오류 증거 확인. 이번 개발 검증에서 이 단계는 수행하지 않음.
