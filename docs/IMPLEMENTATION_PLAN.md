## 2026-10-23: 사내 MCP 등록과 설계 배치 정비

회사 네트워크가 사용자 접근과 외부 통신을 통제한다. 앱과 내보낸 실행기에 별도 사내 주소 허용 목록을 추가하지 않고 HTTP/HTTPS 사내 호스트·IP·사용자 지정 포트를 지원한다. 기존 검증된 세션과 자료별 읽기/소유자 수정 권한은 유지한다.

MCP 실행 정의는 ‘도구 및 자료’에서 등록한다. 기존 `content` 안에 `flowlyMcp.version=1` 형식으로 연결 ID, 주소/토큰 환경 변수 이름, 도구 이름·효과·입력 스키마를 저장한다. 키·토큰 값은 받지 않는다. 현재 접근 가능한 자료에서만 내보내기 연결을 만들고, 공유받은 자료의 외부 자격 증명은 상속하지 않는다. 공개 MCP 기본 연결 및 예전 서버 환경 연결의 자동 내보내기를 제거한다. 예전 자유 텍스트 자료는 보존하고 도구 정의가 필요함을 표시하며 대표 예제의 고정 계약은 호환해서 읽는다. DB 구조·워크플로 JSON 버전은 유지한다.

노드 배치는 공통 DAG 의존 순서를 사용하며 좌표만 바꾼다. 노드·연결 배열, 매핑·분기·하위 작업 순서는 바꾸지 않는다. 편집기의 명시적인 자동 정렬은 되돌릴 수 있고, 기존 사용자 저장 배치를 열 때 임의로 덮어쓰지 않는다. 연결선은 노드 영역을 우회하고 새 노드는 빈 위치에 추가한다. 예제와 편집기의 도식 기준을 통일한다.

Harness는 답변과 출처가 공백만인 경우를 거절하는 `not_blank` 평가 규칙을 사용한다. 최초 응답과 한 번의 수정 응답 모두 검사한다. 설계 실행 검증은 Node.js·Python 생성 ZIP을 실제 프로세스로 실행하고 모델·MCP 경계만 별도 테스트 응답으로 대체한다. 외부 서비스 연결 없이 수행하며 실제 모델 품질과 사내 서비스 호환성 검증으로 표현하지 않는다. 최종 명령·수치는 [EXAMPLE_VALIDATION.md](EXAMPLE_VALIDATION.md)에 기록한다.

이전의 ‘3,200개 고유 워크플로 완료’ 판정을 철회한다. 기존 3,200개는 서로 다른 자연어 업무 계약이었고, 실행 그래프를 정규화하자 구조 6개·실행 설정 8개 그룹이었다. 과거 CLI 검사는 해당 공통 실행기의 작동을 확인했을 뿐 구조의 다양성을 증명하지 않았다.

예제 UI/API에는 개별 설계하고 구조를 비교한 워크플로만 제공한다. 실제 공개·검증·남은 수는 [현재 집계](EXAMPLE_CATALOG_INVENTORY.md)를 따른다. 재설계 전 원본은 저장소의 JSON 아카이브로 보존한다. ‘업무 사례 · 구조 재설계 대기’ 탭은 제공하지 않는다. 인증된 `GET /api/examples?view=cases`는 410이며, 공개 설계에 없는 기존 사례 ID의 상세 조회·복제·직접 다운로드는 404다. 사용자가 이미 복제한 워크플로와 자료는 수정·삭제하지 않는다. 3,200개 개별 실행 설계 목표는 미완료다.

각 설계는 노드·연결선·중첩 작업·데이터 매핑·조건·실패 경로와 정상/경계 시나리오를 직접 정의한다. 이름·문구·좌표·프레임워크 교체와 같은 구조의 설정 변경은 독립 예제로 인정하지 않는다. 불필요한 노드·변환·분기·중첩을 추가해 숫자를 채우는 것도 금지한다. 업무에 필요한 제어 흐름·데이터 전달의 실질 차이와 이를 보여 주는 정상·경계 실행 증거가 있어야 한다. 구조 또는 실행 설정이 중복이면 빌드를 거절하며, 구조 서명이 달라도 노드의 실질 기여는 별도 검토한다.

조건 노드에 값 비교를 추가한다. 숫자/문자/불리언을 구분하고, 기준값 또는 다른 입력 경로와 비교한다. 누락 경로나 잘못된 자료형은 실패한다. 웹의 미리보기는 실제 입력 평가를 흉내 내지 않으며, 실제 평가는 내보낸 Node.js/Python 실행기가 담당한다.

검증은 실제 ZIP CLI의 입력 전달, 실행/건너뜀 경로, 반복, 사람 검토와 재개, 기억 상태를 검사한다. 모델 HTTP 경계에만 테스트 응답을 주입하고 다른 네트워크는 차단한다. 제품 ZIP에는 테스트 응답이나 키를 포함하지 않는다. 예제 제공 범위를 바꾼 뒤 Node.js/Python 검증을 현재 소스로 다시 수행하고, 이전 지문의 통과 결과는 승계하지 않는다. 최신 확정 결과는 [검증 기록](EXAMPLE_VALIDATION.md)과 [집계](EXAMPLE_CATALOG_INVENTORY.md)를 따른다. 외부 모델·MCP 호출과 기존 키 접근은 하지 않는다.

## 2026-10-22: 누락 확장과 운영 기능 구현 · v5

기존 제안 32개를 [FEATURE_SPEC.md](FEATURE_SPEC.md)의 하나의 표에 최초 상태(`구현됨·보강 필요·신규 개발·후순위`), A/B/C 우선순위, 현재 구현 범위로 정리했다. 파일·노드 계약을 먼저 나누고 A의 검사·호환성, B의 데이터 처리·검토·운영, C의 확장·복구 순서로 구현했다. 웹은 OpenAI를 호출하지 않으며 기존 편집기·자료 권한·Vinext/Workers/D1·pnpm을 유지했다.

### 구현 범위

- 팔레트 **28종**, 템플릿 **27개**, 핵심 용어 **40개**. 새 별도 노드는 파일 입력·문서 내용 추출·민감정보 필터·답변 평가·파일 출력·자동 시작·보상 작업 7종이다. Agent/에이전트 중복을 만들지 않았다.

- 실제 파일 읽기·해시 재검사·CSV/XLSX/PDF/DOCX 출력·한국어 OCR을 로컬 파일로 검증했다. Node의 파일 처리도 공용 Python 하위 프로세스를 사용한다. 필요한 파일 라이브러리·OCR 엔진/언어 데이터가 없으면 미설정이다.

- 워크플로 불변 발행·비교·초안 복원·지정 버전 ZIP, 자료 댓글, 저장 충돌 보존/최신본 확인/복사, 감사 이력을 구현했다. D1 `0002_workflow_history.sql`을 로컬에 적용했다. 발행본도 내보내기 시점에 현재 자료 권한을 검사한다.
- 복원된 오래된 원장이 완료된 외부 변경을 재실행할 수 있는 문제를 교차 검사에서 발견했다. 쓰기 도구가 있는 패키지의 복원 기록을 조회 전용으로 표시하고 결정·재개·직접 엔진 실행을 막는다. 새 실행 전 외부 결과 확인이 필요하며 백업 복원을 자동 복구와 동일하게 취급하지 않는다.
- 실행별 모델/임베딩 모델 설정 고정, 안전한 취소 파일, 스트림에 걸쳐 분할된 서비스 토큰 삭제, 파일 정션/경로 이탈·출력 덮어쓰기 차단, 공용 산출물 관리 시 모든 프로필 잠금을 보강했다.

- 동일 루트 실행의 하위 작업 전체에서 같은 도구·인자의 외부 쓰기 이력을 확인한다. 완료 이력은 이후 거절로 덮어쓰지 않으며, 저장 실패·불명확한 외부 결과·취소·권한·한도 오류는 일반 오류 경로로 우회하지 않는다.

- 웹 미리보기는 양식 입력과 하위 자료 참조를 검사하고 새 노드의 역할을 설명한다. 실제 분류·검토·병렬 처리나 기억 저장 결과를 생성했다고 표시하지 않는다.
- 모델 필요 여부·도구 선택·자료 권한·키 제외를 중첩 정의 전체에 적용한다. 웹 OpenAI 호출 차단과 사용자 직접 로컬 키 설정 정책은 그대로다.
- 내보내기 전체의 자료·서비스 연결은 각각 100개까지 허용한다. 하위 정의를 합산해 웹 점검과 서버에서 다운로드 전에 거절하고 Node/Python에서도 같은 경계를 검사한다.

### 실제 외부 호출

공개 `https://developers.openai.com/mcp`에서 `fetch_openai_doc`의 `url`·`anchor`로 공식 함수 호출 문서의 `#parallel-function-calling` 문단을 읽었다. 응답 JSON은 921 UTF-8 bytes였다.

- 실제 MCP POST **6회**: `initialize` 2, 초기화 알림 2, `tools/list` 1, `tools/call` 1. 이 가운데 읽기 도구 실행 **1회 성공**.
- OpenAI 모델 호출 **0회**. OpenAI API 키 복사·생성·등록·사용 **0회**.
- 사용자가 내보낸 프로젝트에 직접 본인의 키를 설정한다. 웹에는 키를 등록하지 않는다.
- 공개 MCP의 독립 읽기 검증은 실제 모델 → 도구 → 최종 답변 검증과 다르다. 후자는 미완료다.

| F02 | 실행 상세 GET 폴링·새로고침 | 저장 상태 복원, 실행 중복 없음; 스트림 커서 방식은 미구현 |
| F03 | 실행 중 워크플로 초안 수정 | 시작 시 고정된 버전으로 계속 실행 |
| F04 | Run·Approval·Checkpoint ID 바꿔 접근 | 사용자 범위 검사로 거절 |

## Codex의 Agentic 개발 분담

개발 도구의 병렬 에이전트 활용은 제품의 다중 에이전트 기능과 별개다. 사용 중인 Codex 환경에서 병렬 작업이 가능하면 다음과 같이 나눈다. 가능하지 않으면 동일 책임 구분으로 순차 진행한다.

| 담당 | 책임 | 파일 충돌 방지 |
| --- | --- | --- |
| 통합 담당 | 요구사항·API 계약·스키마·마이그레이션·최종 통합 | 공유 타입과 DB 변경의 단일 담당 |
| UI 담당 | Agent 설정, 연결 관리, 실행·승인 화면 | UI 디렉터리 중심 |
| Runtime 담당 | 그래프 실행, MCP 어댑터, 체크포인트, 재시도 | runtime 디렉터리 중심 |
| 검증 담당 | 권한·실패·재개 시나리오, 보안 경계 리뷰 | 테스트와 읽기 전용 리뷰 중심 |

한 번에 모든 역할을 가동하기보다 마일스톤의 독립 작업만 병렬화한다. 데이터 모델과 인증 설계를 각 에이전트가 따로 바꾸지 않는다.

타입·린트·빌드·HTTP·Node/Python 실행기 회귀 검사를 완료했다. 실제 모델 검증은 사용자가 내려받은 프로젝트에서 본인 키를 직접 설정한 뒤 수행한다. 웹 운영 배포에는 OIDC/Sites 공급자와 운영 D1·인증 비밀·보존·백업 설정을 별도로 준비한다.

최종 공식 문서 예제 ZIP: `outputs/flowly-node-project.zip`, `outputs/flowly-python-project.zip`. 로컬 개발용 Alice 식별자와 공개 문서 연결만 포함하며 키는 비어 있다. 웹의 내보내기를 사용하면 현재 로그인 계정과 현재 워크플로로 새 ZIP을 받는다. 로컬 서버는 `pnpm start`로 127.0.0.1:5173에서 실행 중이며, 소스 변경 자동 재빌드가 필요하면 이 서버를 종료하고 `pnpm dev`를 사용한다.
