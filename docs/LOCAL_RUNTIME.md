# 로컬 개발과 내보낸 프로젝트 실행

갱신: 2026-10-24. 현재 제품 정책은 **웹에서 설계·자료·공유·발행 버전 관리와 내보내기, 다운로드한 Node.js/Python 프로젝트에서 사용자 본인의 키로 실제 실행**입니다. 웹의 OpenAI 모델 호출은 설정 유무와 관계없이 차단합니다. 현재 v5 정의는 31종 노드를 지원하며 v1~v4 JSON은 명시적인 변환으로 읽습니다.

## 환경과 저장 경계

웹앱은 React·TypeScript·Vinext·Cloudflare Workers·Drizzle·D1을 유지합니다. Node.js/Python은 내려받은 실행 프로젝트의 환경이며 웹 서버나 DB를 교체한 것이 아닙니다. 기존 Sites 호스팅 설정은 보존했지만 신뢰 프록시 인증 연결을 포함한 실제 Sites 배포는 검증하지 않았습니다.

현재 디렉터리는 Git 작업 트리이며, P0 작업 시점의 소스 파일은 미추적 상태입니다. 이번 작업에서 커밋·PR·원격 배포는 생성하지 않았고, 참고로 제공된 다른 프로젝트는 변경하지 않았습니다.

| 위치 | 저장하거나 처리하는 내용 |
| --- | --- |
| 웹 D1 | 사용자 자료·공유·댓글·워크플로·발행 버전·감사 기록·미리보기, 기존 개발 테스트 실행·체크포인트 |

| 내보낸 폴더의 `.env` | 사용자가 직접 입력한 OpenAI 키·필요한 본인 서비스 토큰 |

## 웹앱 개발 환경 시작

```powershell
pnpm install --frozen-lockfile
pnpm setup:local
pnpm db:migrate:local
pnpm dev
```

기본 주소는 `http://127.0.0.1:5173`입니다. `localhost`로 바꾸면 세션 출처가 달라집니다. `setup:local`은 `.dev.vars`가 없을 때 테스트 인증 설정·서명 키를 생성하며 기존 파일을 덮어쓰거나 키 원문을 출력하지 않습니다. 웹 개발을 위해 OpenAI 키를 등록하지 않습니다.

고정 계정은 `test:alice`, `test:bob`, `test:carol`이고 이메일은 각각 `alice@flowly.test` 등입니다. 테스트 로그인은 명시적인 개발·테스트 환경과 루프백 주소에서만 허용됩니다. 요청에 임의 사용자 ID를 넣어 계정을 만들 수 없습니다. 실제 OIDC 사용자와 테스트 사용자는 ID 접두사와 저장 범위가 다릅니다.

`.wrangler/state`는 로컬 D1 저장소입니다. `pnpm dev`는 실행기 소스를 생성하고 Vinext 빌드 후 Wrangler를 시작합니다. 소스 변경 시 기존 서버를 종료하고 재빌드하므로 잠시 연결이 끊깁니다. Windows 출력 디렉터리 잠금을 피하기 위한 구성입니다. 빌드 결과만 실행하려면 다른 서버를 종료하고 `pnpm build`, `pnpm start`를 사용합니다. `pnpm dev:hmr`는 기존 Vite 경로이며 이번 환경에서는 최초 시작 지연이 있었습니다.

`pnpm db:migrate:local`에는 `0002_workflow_history.sql`도 포함됩니다. 이 마이그레이션은 발행 버전·댓글·감사 기록 테이블과 발행본 UPDATE 차단을 추가합니다. 기존 DB를 사용하는 경우 서버를 시작하기 전에 적용하세요.

## 기본 사용자 흐름

1. 로그인하고 대표 예제를 선택하거나 입력 → Agent → 답변 흐름을 만듭니다.
2. **도구 및 자료 → MCP**에 사내 연결의 주소·도구 정의·환경 변수 이름을 등록하고 Agent의 허용 도구로 선택합니다. 예제의 계약과 실제 사내 서비스의 도구 이름·인자·결과가 일치해야 합니다.
3. **미리보기**로 연결 구조와 자료 접근을 점검합니다. 여기서는 모델이나 MCP 서비스를 호출하지 않습니다.
4. **실행 프로젝트 내보내기**에서 Node.js 또는 Python을 선택해 ZIP을 다운로드합니다.
5. ZIP을 새 폴더에 풀고 아래와 같이 환경 파일을 복사합니다.

```powershell
Copy-Item .env.example .env
```

로컬 편집기에서 `.env`를 열어 `OPENAI_API_KEY`의 빈 값에 본인의 키를 입력하고 `FLOWLY_MODEL`을 지정합니다. 기본 예시는 `gpt-5.4-mini`입니다. Responses API 함수 호출과 `reasoning.effort=none`을 지원하는 모델을 사용합니다. 키는 웹·채팅·워크플로 JSON·Git에 넣지 않습니다. 실행기는 지정된 `.env` 파일을 읽으며 다른 프로세스 환경에 있는 키를 자동으로 대신 사용하지 않습니다.

```dotenv
OPENAI_API_KEY=
FLOWLY_MODEL=gpt-5.4-mini
```

위 예제는 의도적으로 키가 비어 있습니다. 실제 키가 없거나 모델 설정이 없으면 미설정 오류로 중단하고 가짜 답변으로 대체하지 않습니다. 사내 MCP의 실제 주소와 본인 토큰은 `.env.example`과 `START_HERE.md`에 표시된 정확한 `FLOWLY_MCP_ENDPOINT_...`·`FLOWLY_MCP_TOKEN_...` 변수에 입력합니다. 웹에 등록한 공유 연결 정의가 다른 사용자의 서비스 자격 증명을 제공하지는 않습니다.

Node.js 22.13 이상 또는 Python 3.11 이상에서 해당 프로젝트 폴더를 열고 실행합니다. 기본 AI·데이터 실행기는 추가 패키지 설치 없이 사용할 수 있습니다. 파일 처리에는 형식별 라이브러리·OCR 엔진이 필요하고, Node 프로젝트라도 파일·운영·트리거 도우미에는 Python 3.11 이상이 필요합니다.

```powershell
# Node.js ZIP을 선택한 경우
node runner.mjs run --input "사내 기술 자료에서 병렬 작업의 검증 기준을 찾아 줘"
node runner.mjs run --input-file input.txt

# Python ZIP을 선택한 경우
python runner.py run --input "사내 기술 자료에서 병렬 작업의 검증 기준을 찾아 줘"
python runner.py run --input-file input.txt
```

실제 모델과 도구 호출은 이 명령부터 발생할 수 있습니다. 사용자 입력·작업 지침·연결 자료·도구 결과가 외부 모델과 선택한 서비스에 전송되고 사용 비용이 발생할 수 있습니다. 이 개발 과정에서는 기존 OpenAI 키를 프로젝트에 복사하거나 생성·등록·사용하지 않았으며, 모델 호출을 포함한 전체 실제 실행은 아직 검증하지 않았습니다.

## 실행 상태·승인·재개

### 설정 검사와 보고서

```powershell
node runner.mjs check
python runner.py check
node runner.mjs report <실행ID> --output report.html
python runner.py report <실행ID> --output report.html
```

`check`는 패키지 형식·자료·도구 인자·필요한 로컬 변수 이름을 검사합니다. `ready`는 오프라인 설정 검사 통과이며 원격 연결 성공이나 모델 사용 권한을 뜻하지 않습니다. `unconfigured`는 필수 설정 누락, `invalid`는 형식 오류입니다. 값 원문은 출력하지 않습니다. `report`는 원본 패키지와 저장 기록이 일치할 때 HTML을 신규 생성하며 `.env`를 읽거나 외부 호출을 하지 않습니다. 기존 파일은 덮어쓰지 않습니다.

### 모델 없이 실행하는 흐름

하위 작업을 포함해 AI 답변·Agent·AI 분류·작업 조정·모델 평가·벡터/웹 검색이 없는 흐름은 OpenAI 키가 필요하지 않습니다. **JSON에서 필요한 값 고르기** 템플릿을 내보내고 `input.txt`에 `{"name":"민수","task":"회의록 정리"}`를 넣으면, `run --input-file input.txt`가 실제 값을 변환·결합해 출력합니다. 직접 도구 실행도 모델 없이 동작하지만 등록한 사내 MCP의 주소·필요 토큰은 설정해야 합니다. 규칙 평가·로컬 기억·단어 검색·등록 계산 프로그램은 모델 없이 동작합니다.

**문서에서 근거를 찾는 답변**은 검색→AI 흐름이므로 모델 키가 필요합니다. 문서 검색의 기본 방식은 선택한 텍스트를 조각내어 단어로 비교하며 조각 내용·자료 ID·버전·출처를 반환합니다. 관련 문서가 없으면 근거 없음으로 표시합니다.

검색 방식을 `vector`로 바꾸면 실제 임베딩 API와 로컬 벡터 캐시를 사용합니다. 기본 임베딩 모델은 `text-embedding-3-small`이고 `.env`의 `FLOWLY_EMBEDDING_MODEL`로 바꿉니다. 임베딩만 사용하는 흐름에는 `OPENAI_API_KEY`가 필요하지만 `FLOWLY_MODEL`은 필요하지 않습니다. 문서 캐시는 소유자·워크플로·자료 내용·임베딩 모델별로 나누며 질문 임베딩은 매 실행 호출합니다. `web` 방식은 Responses 웹 검색 도구의 완료와 HTTPS 출처를 확인합니다. 두 방식 모두 실제 사용량과 실행 한도를 적용하며, 계정 권한·연결·응답 품질은 별도로 검증해야 합니다.

### 계산·검증 프로그램

`program`은 `numeric_summary`·`schema_check`·`schema_patch`·`evidence_check`·`goal_check`·`rank_fusion`의 여섯 등록 프로그램만 실행합니다. 숫자 집계, 스키마 검사, 오류 필드만 수정한 뒤 재검사, 출처/버전/인용 대조, 완료 조건 검사, 검색 순위 통합을 실제 계산합니다. 고정 `arguments`와 입력 경로 `bindings`를 받아 `{text:결과 JSON 문자열,data:결과 객체}`를 출력하며 다음 조건 노드에서 결과를 검사할 수 있습니다.

프로그램 자체는 파일·네트워크·프로세스·임의 코드·SQL을 실행하지 않습니다. Node.js ZIP에는 구현을 번들하고, Python ZIP에는 해당 노드가 있을 때 `flowly_programs.py`를 포함합니다. 별도 키나 추가 라이브러리는 필요하지 않습니다. 근거 대조는 정확한 출처와 인용 일치를 검사하며 사실성 전체를 판정하지 않습니다. 자세한 입력·한도는 [P2_PROGRAMS.md](P2_PROGRAMS.md)를 따릅니다.

### 승인과 재개 명령

Node.js 명령 예시입니다. Python에서는 `node runner.mjs` 대신 `python runner.py`를 사용합니다. 실행 명령이 출력한 실행 ID와 승인 ID를 입력합니다.

```powershell
node runner.mjs status <실행ID>
node runner.mjs approve <실행ID> <승인ID>
node runner.mjs deny <실행ID> <승인ID>
node runner.mjs resume <실행ID>
```

`approve`와 `deny`는 결정만 저장합니다. `resume`을 실행해야 다음 처리를 진행합니다. 쓰기는 승인 전에 실행하지 않으며 승인 객체는 실행·사용자·도구·정규화된 인자 해시·만료 시각에 연결됩니다. 기본 승인 유효 기간은 30분입니다.

Node 기록은 `.flowly-runs`, Python 기록은 `.flowly-python-runs`에 저장됩니다. 두 실행기는 기록 형식을 서로 공유하지 않습니다. 시작했던 `workflow.json`이 바뀌면 기존 실행의 상태 확인·재개를 거절하므로 원본을 보관하고 새 자료는 새 프로젝트로 내보냅니다. 종료된 프로세스의 잠금만 남았을 때 `node runner.mjs unlock` 또는 `python runner.py unlock`을 사용합니다. 살아 있는 다른 실행기의 잠금은 강제로 해제하지 않습니다.

새 실행은 비밀이 아닌 답변 모델명·임베딩 모델명을 고정해 기록합니다. 재개 시 필요한 모델 설정이 달라졌으면 외부 호출 전에 중단하며 같은 모델의 키 교체는 허용합니다. 과거 모델 설정 기록이 없는 실행은 호환성을 유지합니다. `status`·승인 결정·`report` 명령은 모델에 연결하지 않습니다.

두 실행기는 모델명의 앞뒤 공백을 제거하고 비교합니다. `FLOWLY_EMBEDDING_MODEL`이 생략되거나 빈 값/공백이면 `text-embedding-3-small`을 사용합니다. 필수 모델명·키가 없는 경우는 계속 미설정입니다. P0 보정은 새 ZIP부터 적용되며, 이미 다운로드한 프로젝트는 재내보내기해야 합니다.

실행기는 호출 전에 진행 상태를 저장하고 완료된 쓰기를 반복하지 않도록 합니다. 외부 쓰기 후 결과가 유실되면 `unknown_outcome`으로 중단하고 자동 재시도하지 않습니다. 사용자가 해당 서비스에서 결과를 확인해야 합니다. 실제 외부 쓰기를 이용한 검증은 아직 수행하지 않았습니다.

### 보완 입력 대기와 재개

입력 양식의 `form.mode`를 `request`로 설정하면 실행 중 필요한 값을 요청하고 `waiting_input`으로 저장합니다. 설정을 생략하면 기존 시작 입력 방식인 `initial`을 유지합니다. 요청 안내·필드·기한은 노드에서 정하며 기한의 기본값은 1,440분, 허용 범위는 1~10,080분입니다. `status`에서 요청 ID와 필수 필드를 확인하고 JSON 객체 파일을 준비합니다.

```powershell
node runner.mjs status <실행ID>
node runner.mjs submit <실행ID> <요청ID> --values-file values.json
node runner.mjs resume <실행ID>

# Python ZIP
python runner.py status <실행ID>
python runner.py submit <실행ID> <요청ID> --values-file values.json
python runner.py resume <실행ID>
```

`submit`은 소유자·요청·노드 설정·입력 해시·기한·필드 형식·출력 스키마를 검사하고 값을 저장합니다. 누락·공백뿐인 필수값·잘못된 형식은 제출되지 않으며 값을 보완해 다시 제출할 수 있습니다. 동일 제출의 반복은 같은 결과를 유지하고 다른 값으로 이미 제출한 요청을 덮어쓰지 않습니다. 유효한 기한 안에 제출한 값은 기한 후 재개해도 보존합니다. 아직 제출하지 않은 요청이 만료되면 중첩 상위 상태에도 만료를 반영합니다.

중첩 작업의 요청도 최상위 실행 ID로 처리합니다. 제출만으로 모델·MCP를 호출하지 않으며 `resume`이 같은 실행과 저장된 지점에서 계속합니다. 완료한 병렬 작업과 쓰기 결과는 반복하지 않습니다. 종료한 실행이나 조회 전용 복원 기록은 제출로 되살리지 않습니다. 사람 검토의 `accept`·`reject`, 외부 변경 승인의 `approve`·`deny`와는 별도 절차입니다.

### 사람 검토와 하위 작업

사람 검토는 외부 변경 승인과 별개입니다. `waiting_review` 결과의 검토 ID를 확인합니다. 수정이 허용된 경우에만 입력 JSON 객체를 바꿀 수 있습니다. 검토 기한은 설정한 1~1,440분이며 대기 시간은 실행 시간 한도에 포함되지 않습니다.

```powershell
node runner.mjs accept <실행ID> <검토ID>
node runner.mjs accept <실행ID> <검토ID> --edited-input-file edited.json
node runner.mjs reject <실행ID> <검토ID>
node runner.mjs resume <실행ID>
```

Python도 같은 명령을 제공합니다. 수락은 `yes`, 거절은 `no` 경로를 활성화합니다. 검토 수정값은 입력·출력 스키마를 통과해야 합니다. 기한 안에 저장한 검토 결정은 기한 후 재개할 때도 유지하며, 외부 변경 승인의 실행 만료 규칙과는 구별합니다. 하위 작업에서 발생한 승인·검토도 최상위 실행 ID로 처리하며, `status`와 `report`에 하위 작업별 상태·결과가 표시됩니다.

병렬 작업과 병렬 팀은 최대 4개 작업을 동시에 실행합니다. 순차 팀은 이전 역할의 출력 `previous`와 누적 출력 `results`를 다음 역할에 전달하며, 첫 역할과 병렬 역할에서는 각각 null과 빈 배열입니다. 반복 노드는 최대 20개 항목과 동시 수 한도 안에서 처리합니다. 넘치는 목록을 조용히 잘라 실행하지 않습니다.

각 묶음은 부모의 남은 판단·도구·토큰 한도를 하위 작업에 나누어 저장합니다. 사용하지 않은 몫을 자동으로 다른 작업에 재배분하지 않습니다. 전체 활성 시간과 노드별 한도도 적용됩니다. 기본 전체 한도는 모델 판단 8회, 도구 12회, 토큰 8,000, 활성 시간 120초이며, 더 큰 작업은 실행 전에 패키지의 `limits`를 허용 범위 안에서 조정해야 합니다. 실행 중에는 패키지를 바꾸지 마세요.

작업 조정의 단일 계획 방식은 모델이 허용 목록 안에서 순서를 한 번 선택하고 저장합니다. 적응형 방식은 완료한 결과를 보고 다음 작업 또는 완료를 판단하며 최대 8라운드·라운드별 작업 수·전체 실행 한도를 지킵니다. 계획과 결과를 저장하므로 재개 시 완료된 계획을 임의로 다시 만들지 않습니다. 한도 안에서 완료 판단을 하지 못하면 성공으로 표시하지 않습니다. 하위 흐름은 고정된 정의 복사본이며 중첩 3단계·전체 정의 120노드까지만 허용합니다. 오류 분기는 일반 처리 오류만 받으며 권한·저장·취소·한도·불명확한 외부 변경 결과는 우회하지 못합니다.

적응형 `maxRounds`를 생략하면 Node.js·Python 모두 **3라운드**를 사용합니다. 명시적 설정 범위는 1~8입니다. 완료 판단·실행 예산·오류가 먼저 도달하면 중단하며, 기본값 때문에 무조건 3라운드를 실행하지 않습니다.

작업별 `dependsOn`에는 같은 작업 조정 노드에 등록한 선행 작업 ID를 지정합니다. 순환·없는 작업·선행 작업 누락/역순 계획을 거절하며, 다음 작업에는 선언한 선행 결과만 `artifacts`로 전달합니다. `completion`은 `{input,artifacts}`에 대해 명시한 조건을 평가하므로 모델이 완료라고 말해도 조건을 통과하지 못하면 성공으로 바꾸지 않습니다. 작업 정의와 입력 해시가 같은 완료 결과는 재사용하고 완료한 변경 작업을 다른 입력으로 다시 실행하도록 자동 재계획하지 않습니다. 실행 중 임의 새 역할 생성, 분산 작업 점유, 자료 버전 변경에 따른 모든 종속 산출물 무효화까지 구현한 것은 아닙니다.

기억 노드는 로컬 저장 또는 허용한 MCP 도구를 선택합니다. 로컬 읽기·쓰기·삭제는 소유자와 최상위 워크플로별로 격리하고, 실행/노드별 작업 ID와 결과를 원자적으로 저장해 재개 시 재사용합니다. 선택적인 TTL이 지나면 읽기 결과를 미발견으로 처리합니다. MCP 기억은 `namespace/key/action/value/expiresAt` 계약의 도구가 필요하며 소유자+최상위 워크플로의 namespace를 강제합니다. 원격 쓰기·삭제에는 승인이 필요하고 서비스도 만료 계약을 지원해야 합니다. 로컬 기억을 자동으로 원격에 동기화하거나 암호화하지는 않습니다.

답변 출력의 스트리밍 설정은 Responses SSE의 부분 텍스트를 저장 이벤트와 CLI 표준오류 JSONL로 전달합니다. 표준출력은 최종 JSON 결과를 유지하며, 완료 응답과 사용량을 확인하기 전에는 부분 결과를 최종 답변으로 표시하지 않습니다. 보상 작업은 완료한 외부 쓰기를 대상으로 별도 도구와 새 승인을 사용합니다. 모든 변경을 자동으로 되돌리는 기능은 아닙니다.

### 기술·DB 통합 대표 예제

`p4-approved-database-change`는 DB 상태 조회→버전에 묶인 변경 승인→독립 검증→통과 또는 별도 승인 복구를 실행합니다. `p4-goal-technical-team`은 기술 근거→코드 구현·시험·독립 검토→승인된 코드 적용→DB 변경을 의존 관계로 연결하고 각 작업의 산출물로 최종 완료를 검사합니다. 실제 시험 실패 또는 검토 거절이면 코드 적용과 뒤따르는 DB 변경으로 진행하지 않습니다. 복구 성공은 원래 변경 목표를 달성한 성공과 구별합니다.

이 예제의 사내 MCP 계약은 ‘도구 및 자료’에 등록하고 ZIP의 `.env`에서 `FLOWLY_MCP_ENDPOINT_ENGINEERING`과 `FLOWLY_MCP_TOKEN_ENGINEERING`을 채웁니다. 제품 ZIP에는 등록 도구의 계약만 들어가며 사내 서비스 구현은 별도 준비해야 합니다. 테스트의 `p4-local-tools.py`는 임시 폴더에서 고정 Python 함수 시험·SQLite 백업/변경/복구를 수행하는 검사 도우미이고 제품에 포함하지 않습니다. 범용 코드 샌드박스나 DB 서버가 ZIP에 내장되었다는 뜻이 아닙니다.

## 파일·OCR와 로컬 자동 시작

파일 입력은 `inputs/` 아래 상대경로와 파일 해시를 확인합니다. 문서 처리는 텍스트·CSV·PDF·DOCX·XLSX의 본문/표와 이미지·PDF OCR을 지원하며, 형식·크기·페이지 한도를 적용합니다. DOCX는 Word 인쇄 페이지를 계산하지 않고 문서 위치를 표시합니다. 파일 출력은 `outputs/` 아래 실행별 폴더에 CSV·XLSX·PDF·DOCX를 새로 만들며 기존 파일 덮어쓰기와 동일 작업의 중복 생성을 차단합니다.

파일 노드가 있는 ZIP에는 `flowly_files.py`와 `requirements-files.txt`가 포함됩니다. Node 파일 노드도 이 Python 도우미를 사용합니다.

```powershell
python -m venv .venv-files
.venv-files\Scripts\python -m pip install -r requirements-files.txt
```

Node에서는 `.env`의 `FLOWLY_PYTHON`을 이 가상 환경 Python 실행 파일의 절대경로로 지정합니다. Python 파일 흐름은 `.venv-files\Scripts\python runner.py ...`로 실행합니다. macOS/Linux 가상 환경 경로는 `.venv-files/bin/python`입니다. OCR에는 별도 Tesseract 실행 파일 또는 호환 tesserocr 패키지와 `tessdata/kor.traineddata`·`eng.traineddata`가 필요합니다. ZIP README의 설치 안내를 따르세요. `check`는 선택한 방식의 누락된 라이브러리·엔진·언어 데이터를 표시하며 자동 설치하거나 외부 OCR 서비스로 대신 보내지 않습니다.

민감정보 필터는 선택한 이메일·전화·주민등록번호·카드·비밀 패턴을 가리거나 제거하거나 차단합니다. 발견 원문은 결과에 다시 쓰지 않지만 모든 개인정보를 탐지하거나 앞 단계에 이미 저장한 기록을 지우지는 않습니다. 평가 노드는 문자열·길이·JSON 규칙 또는 모델 평가를 실행하며 전체 사실성을 보장하는 판정으로 사용하지 않습니다.

자동 시작 노드가 있는 ZIP에는 `flowly_triggers.py`가 포함됩니다. 사용자가 직접 실행해야 예약·웹훅·이벤트를 받습니다.

```powershell
# 예약 방식
python flowly_triggers.py schedule --max-runs 10 --input-file input.txt
# 웹훅 또는 이벤트 방식
python flowly_triggers.py serve --port 8789
python flowly_triggers.py status
```

예약은 UTC 시작 시각·간격과 지속 기록을 사용하며 놓친 시각의 실행을 한꺼번에 재생하지 않습니다. 웹훅/이벤트는 `.env`의 `FLOWLY_TRIGGER_SECRET`, HMAC·타임스탬프·이벤트 ID·본문 해시를 검사합니다. 같은 수신을 중복 실행하지 않으며 불명확한 결과는 자동 재시도하지 않습니다. 리스너는 `127.0.0.1`에만 열고 외부 수신 프록시는 사용자가 별도로 구성합니다. 웹의 개발용 Cron과는 별개입니다.

## 내보내기와 자료 권한

`POST /api/export`는 검증된 세션에서 사용자 ID를 얻습니다. 같은 출처의 JSON 요청만 허용하며 Worker 입구에서 API 본문을 350KB·10초로 제한합니다. 현재 초안 또는 소유자의 지정 발행 버전을 선택해 그래프를 검증하고 현재 접근 가능한 참조 자료를 다시 조회합니다. 클라이언트가 제출한 소유자·자료 본문·도구 정책을 신뢰하지 않습니다.

내보내는 연결은 사용자의 연결 정의 중 하위 작업을 포함한 그래프가 선택한 도구만 포함합니다. 다른 사용자가 공유한 MCP 정의는 그 사용자의 외부 자격 증명을 제공하지 않습니다. 서버 토큰 값과 공유 대상 이메일 목록은 제외하고 필요한 로컬 토큰 변수 이름만 남깁니다. `test-read`·`test-write`는 실제 실행 프로젝트로 내보내지 못합니다. 자료가 포함된 `workflow.json`은 최대 8MB이고 자료·연결은 각각 100개까지 허용합니다.

ZIP에는 `runner.mjs` 또는 `runner.py`, `workflow.json`, `.env.example`, `README.md`, `.gitignore`와 로컬 운영용 `flowly_ops.py`·`flowly_local.py`·`OPERATIONS.md`가 들어갑니다. 파일 처리·자동 시작 도우미는 해당 노드가 있을 때 포함하고 Python의 등록 프로그램 도우미도 해당 노드가 있을 때 포함합니다. 패키지 형식은 `flowly-executable-export`, 버전 1이며 `language`가 `node` 또는 `python`입니다. 기존 **JSON 내보내기**는 구성 공유용으로 자료 본문·실행기를 포함하지 않아 ZIP과 용도가 다릅니다.

예제 목록의 직접 다운로드와 편집기 내보내기에 같은 구성 규칙을 적용합니다. 예제 ZIP에는 추가로 `example-contract.json`, `input.txt`, `EXAMPLE.md`가 포함됩니다. 양쪽 내보내기는 동일한 검증 manifest에서 `START_HERE.md`·`AI_PROMPT.md`·`AGENTS.md`·`WORKFLOW_GUIDE.md`·`skills/flowly-workflow/SKILL.md`와 선택한 Skill별 `SKILL.md`를 생성합니다. 문서에는 중첩 연결·매핑·분기·선행 작업·완료 조건·허용 도구·한도와 정확한 설정 변수 이름을 담습니다.

외부 AI 도구에 `START_HERE.md`와 `AI_PROMPT.md`를 읽도록 지정하세요. 자동 Skill 설치나 AI 도구별 자동 발견은 보장하지 않으며, 문서가 실행기의 승인·권한·한도 검사를 대체하지 않습니다. 선택한 Skill 원문은 안전한 파일 이름·YAML 문자열·JSON 코드 블록으로 보존하며 상위 정책을 바꾸지 않습니다. 문서 생성기는 환경의 비밀 값을 읽지 않고 내부 사고 원문을 요구하지 않습니다. 자세한 파일 구성은 [P1_AI_EXPORTS.md](P1_AI_EXPORTS.md)를 참고하세요.

**다운로드한 자료는 독립적인 복사본입니다. 웹에서 원본을 수정·삭제하거나 공유를 철회해도 이미 내보낸 자료를 회수하거나 실행 때 원격으로 재검사할 수 없습니다.** 이후의 새 내보내기는 최신 권한을 다시 검사합니다. 민감한 자료가 포함되는지와 사용·재공유 가능한 범위를 확인하고 불필요한 복사본은 사용자가 관리해야 합니다.

`.env`, `.flowly-runs`, `.flowly-python-runs`는 Git 제외 목록에 있지만 암호화된 저장소가 아닙니다. 로컬 실행 기록과 자료에는 입력, 문서 본문, 도구 인자·결과, 오류가 포함될 수 있습니다. 사용자 입력에 포함된 임의의 비밀까지 완전히 탐지하지는 못하므로 프로젝트 폴더나 로그를 그대로 외부에 공유하지 마세요. 커스텀 `--state` 경로를 사용하면 해당 경로도 직접 Git 제외·보관 정책에 추가합니다.

## 웹 발행 버전·댓글·저장 충돌

워크플로 소유자는 저장한 초안을 번호가 붙은 불변 버전으로 발행하고 목록·변경 내용·단일 버전을 확인할 수 있습니다. 복원은 발행본을 바꾸지 않고 현재 초안을 새 저장 시각으로 갱신합니다. 지정 버전 ZIP도 내보내는 시점의 자료 공유 권한과 본인 연결을 다시 검사합니다. 화면의 비교는 발행 시 채워진 기본 입력 매핑·스키마와 초안의 같은 기본값을 동등하게 취급합니다.

기존 워크플로 저장과 자료 수정은 편집을 시작한 `baseUpdatedAt`을 보내야 합니다. 값이 없거나 최신 저장 시각과 다르면 `409`로 거절합니다. 화면은 입력을 유지하며 최신 내용 불러오기 또는 워크플로 별도 복사 저장을 제공합니다. 무조건 자동 병합하거나 다른 편집을 덮어쓰지 않습니다.

자료를 읽을 권한이 있는 사용자는 댓글을 작성·조회할 수 있고 댓글 작성자 또는 자료 소유자가 삭제할 수 있습니다. 공유가 철회되면 댓글 접근도 거절하며 댓글 권한이 원본 수정·삭제 권한을 주지는 않습니다. 자료·공유·워크플로·발행·복원·댓글·내보내기 감사 기록에는 사용자·시각·변경 필드명·공유 범위/대상 수·버전 번호 같은 metadata를 남깁니다. 자료 본문·댓글 원문·토큰은 감사 기록에 복사하지 않으며 조회는 소유자 범위로 제한합니다.

## 내보낸 프로젝트의 로컬 운영

두 언어 ZIP에서 Python 3.11 이상으로 다음 명령을 사용할 수 있습니다. Node 프로젝트의 실행에는 Node.js도 필요합니다.

```powershell
python flowly_local.py --root .
python flowly_ops.py request --root . --request-file operation.json
python flowly_ops.py worker --root . --once
```

`flowly_local.py`는 루프백 관리 화면을 시작합니다. 터미널에 표시한 접근 토큰 포함 주소로 열며, 정확한 Host/Origin과 토큰을 검사합니다. 설정 검사·명시적 원격 점검·대기열·실행 그래프/노드·검색·저장 이벤트·보완 입력 제출·검토·승인·재개·평가·비용 비교·보관 관리가 가능합니다. 비밀 값을 화면에 입력하는 대신 지정한 로컬 `.env` 파일을 편집합니다.

`operation.json`은 프로젝트 내부의 1MB 이하 JSON 요청 파일입니다. 기본 프로필은 `development`와 `.env`이며, 프로필마다 `.flowly-profiles/<이름>/runs`로 실행 상태를 나눕니다. 운영 프로필의 실행·승인·재개·평가·프로브에는 `confirmProduction:true`가 필요합니다. 대기·실행 작업이 있는 프로필의 설정 변경은 차단합니다. 자세한 요청 필드는 [OPERATIONS.md](../export-runtime/OPERATIONS.md)에 있습니다.

```json
{"action":"jobs.enqueue","profile":"development","input":"확인할 내용","priority":0}
```

큐는 SQLite에 지속 저장하고 프로젝트당 worker 하나가 처리합니다. 높은 우선순위와 같은 우선순위의 접수 순서를 따르며 오래 기다린 작업에는 가산점을 줍니다. 이는 노드 안의 최대 동시 4개 처리와 구분됩니다. `worker --once`는 한 작업 후 종료하며, 옵션을 생략하면 명시적으로 중지할 때까지 기다립니다. 보완 입력 제출·승인·검토 결정 후에는 별도 재개 요청이 필요하고 저장 지점에서 중단된 작업을 자동으로 계속 재실행하지 않습니다.

취소는 안전 지점과 HTTP 중단 신호에 연결합니다. 진행 중인 외부 쓰기의 결과를 확인하지 못하면 `unknown_outcome`으로 남기고 자동 재시도하지 않습니다. 직접 실행하는 Node/Python CLI도 `run`·`resume`에 `--cancel-file <프로젝트 안 경로>`를 지정할 수 있습니다. 운영 큐는 이 파일 신호를 관리합니다.

`check`는 오프라인 검사입니다. `probe`는 `target`과 `confirm:true`를 명시해야 실제 외부 호출을 수행합니다. Responses 최소 요청, 벡터 검색을 포함한 프로젝트의 임베딩 점검, MCP 초기 협상·도구 목록·선택 도구 스키마를 확인하고 종류별 전송 시도 수를 반환합니다. MCP `tools/call`은 프로브에서 실행하지 않습니다. 점검 성공은 전체 흐름의 정확성이나 외부 쓰기 권한을 보장하지 않습니다.

평가는 최대 100개 입력 사례를 순차 실행해 기대 문자열 일치/포함 조건·상태·사용량·시간·고정 모델을 기록하고 이전 결과와 비교합니다. 모델이 있는 사례는 사용자가 실행할 때 실제 호출·비용이 발생하며 자동 승인하지 않습니다. 비용은 사용자가 입력한 단가와 기준일로 계산한 범위이며 실제 청구가 아닙니다. 청구 CSV를 수동으로 가져와 기간·모델·통화가 맞는 범위에서 비교하고, 모델별 토큰 분리가 없거나 단가가 미설정이면 정확한 금액을 만들지 않습니다.

### 백업·복원·보존

백업은 선택 프로필의 상태와 선택한 공용 `outputs/`·`reports/`를 `.flowly-ops/backups`에 저장합니다. 환경·키 파일과 현재 비밀 값이 포함된 파일은 제외/거절하며 운영 큐 SQLite 자체는 이 백업 범위에 포함되지 않습니다. 파일 수·개별 크기·전체 크기를 제한하고 같은 패키지·프로필 및 파일별 SHA-256을 확인한 뒤 빈 대상에만 복원합니다. 백업은 암호화하지 않습니다.

**외부 쓰기 도구가 포함된 프로젝트의 복원 실행은 `restoredReadOnly`인 조회 전용 기록입니다.** 오래된 승인 대기 상태로 돌아가 같은 외부 변경을 다시 보내지 않도록 보완 입력 제출·승인·검토 결정·재개를 차단합니다. 상태와 HTML 보고서는 확인할 수 있습니다. 외부 서비스의 실제 결과를 확인한 뒤 필요하면 새 실행을 시작하세요. 읽기·데이터 전용 프로젝트에는 이 복원 제한을 붙이지 않습니다.

기간별 정리에서 입력/승인/검토 대기·불명확 결과·메모리/벡터 원장은 보존합니다. 완료·실패·취소·만료·한도 도달 실행과 선택한 오래된 산출물/보고서가 대상입니다. 공용 폴더 관리 중에는 등록 프로필과 기본 상태 폴더의 실행기 잠금을 잡습니다. 별도 사용자 지정 `--state` 경로로 실행한 프로세스는 먼저 직접 중지해야 합니다. 이 기능은 로컬 사본 관리이며 운영 웹 D1의 자동 백업·복구를 대신하지 않습니다.

## 서비스 연결 정의

**도구 및 자료 → MCP**에서 사내 연결을 등록합니다. 기본 공개 MCP나 서버의 `FLOWLY_CONNECTIONS_JSON`을 웹 내보내기 연결 출처로 쓰지 않습니다. 웹은 정의만 제공하고 실제 서비스 호출은 다운로드한 실행기가 합니다. 사내 접근과 외부 통신 차단은 회사 네트워크가 담당하며 앱에 별도 IP/도메인 허용 목록을 추가하지 않습니다. 기존 로그인·세션 검증·자료 소유권·공유 검사는 유지합니다.

주소, 연결 ID, 주소/토큰 환경 변수 이름, 도구 이름·설명·입력 스키마·읽기/쓰기 구분을 등록합니다. 비밀 값은 입력하지 않습니다. `endpointEnv`와 `tokenEnv`는 다운로드한 폴더의 `.env`에서 사용자가 채울 변수 이름입니다. 신규 정의는 기존 자료 `content` 필드 안에 다음 버전 형식으로 저장하므로 DB 이관이 필요하지 않습니다. 기존 일반 텍스트 MCP는 읽을 수 있지만 실행 도구 정의를 등록해야 내보낼 수 있습니다. 기존 대표 예제의 3개 고정 계약은 호환해서 읽고, 수정 저장 시 새 형식으로 전환합니다.

```json
{
  "flowlyMcp": {
    "version": 1,
    "connectionId": "my-search",
    "endpointEnv": "FLOWLY_MCP_ENDPOINT_MY_SEARCH",
    "tokenEnv": "FLOWLY_MCP_TOKEN_MY_SEARCH",
    "tools": [{
      "name": "search_documents",
      "description": "내 문서에서 검색합니다",
      "effect": "read",
      "inputSchema": {
        "type": "object",
        "properties": {"query": {"type": "string"}},
        "required": ["query"],
        "additionalProperties": false
      }
    }]
  }
}
```

자료 주소 예시는 `http://mcp.intranet:8090/mcp`입니다. 실제 연결하지 않은 형식 예시입니다. 자료에 URL만 등록하는 것만으로 도구 정의가 생기지 않습니다. 허용한 도구 이름과 사내 서버의 입력/응답 계약이 일치해야 합니다. MCP Streamable HTTP initialize·JSON/SSE 도구 호출 범위를 구현했으며, stdio·서버 주도 sampling/elicitation·동적인 도구 탐색·서비스 OAuth UI는 지원하지 않습니다. 조회 도구의 실제 성공과 모델이 도구를 선택해 답하는 전체 실행의 성공은 별도입니다.

HTTP/HTTPS의 사내 호스트·IP·포트를 사용할 수 있습니다. 주소의 기본 형식과 자격 증명·쿼리·프래그먼트 포함 여부만 확인하고 사내 주소 범위를 검사하지 않습니다. 리다이렉트는 따라가지 않습니다. 실행 시작 시 주소를 기록하여 승인 대기 중 주소를 바꾼 뒤 기존 승인으로 재개하는 것을 막습니다. 이것은 주소 허용 목록과 별개의 승인 일관성 검사입니다. 내보낸 프로젝트는 사용자의 기기·네트워크에서 실행됩니다.

## 웹 테스트 엔진과 Cron

기존 `runtime/` TypeScript DAG·Agent 엔진과 D1 `runtime_runs`는 개발 검증 및 이전 기록 조회를 위해 남겨 두었습니다. 외부 모델 대신 결정적인 테스트 모델·가상 도구를 사용하는 실행은 `FLOWLY_ENV=development|test`, `FLOWLY_AUTH_MODE=test`, `FLOWLY_TEST_RUNTIME=true`가 모두 맞을 때만 허용됩니다. 결과는 실제 AI 답변이 아닙니다.

`/api/runtime`의 새 `mode:"live"` 시작은 **항상 거절**합니다. 환경에 OpenAI 키가 있더라도 허용하지 않습니다. Cron이 예전 `live` 실행을 발견해도 `processRun`이 외부 호출 전에 중단합니다. 웹 서버용 OpenAI 키나 모델을 설정해 실제 실행을 켜는 경로는 없습니다.

D1 개발 테스트는 입력·출력 매핑, 한도, 승인, 현재 공유 권한 재검사, 요청 중복 방지, 150초 리스·revision을 이용한 복구를 검사합니다. Cron은 한 번에 최대 3개의 복구 대상을 처리합니다. 로컬 `http://127.0.0.1:5173/__scheduled`는 `--bundle --test-scheduled` 구성으로 개발 예약 함수를 검사하는 경로이며 실제 모델 실행 시작 수단이 아닙니다.

웹 D1의 권한 재검사와 다운로드한 오프라인 프로젝트의 고정 자료 검사는 서로 다릅니다. 원격 공유 철회 검사는 D1 개발 테스트 및 **새 내보내기**에만 적용됩니다. 내려받은 프로젝트가 원격 공유 권한을 계속 확인한다고 보장하지 않습니다.

## 인증과 운영 웹 배포

기본 인증은 미설정입니다. 운영 OIDC에는 `FLOWLY_ENV=production`, `FLOWLY_AUTH_MODE=oidc`, 실제 HTTPS `FLOWLY_APP_ORIGIN`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`와 공급자 등록이 필요합니다. Redirect URI는 `<출처>/api/auth/callback`, scope는 `openid email profile`입니다. 서버 비밀 저장소에는 32자 이상의 무작위 `FLOWLY_SESSION_SECRET`과 `OIDC_CLIENT_SECRET`을 둡니다. 이는 웹 인증용이며 사용자의 실행 프로젝트 OpenAI 키와 별개입니다.

oauth4webapi로 discovery·PKCE·state·nonce·ID 토큰 서명·클레임과 `email_verified:true`를 검사합니다. 계정 ID는 issuer+subject 해시이며 이메일만 같다고 계정을 합치지 않습니다. 세션은 8시간이고 로그아웃은 현재 쿠키를 삭제합니다. 개별 세션 서버 철회 목록은 후속 과제이며 전체 철회에는 서명 키 회전이 필요합니다.

Sites 모드는 HTTPS 출처, `FLOWLY_SITES_ASSERTION_SECRET`, 신뢰 프록시가 발급한 60초 이하 HMAC assertion이 필요합니다. 일반 `oai-authenticated-*` 헤더나 프록시 경유 주장만으로 인증하지 않습니다. 실제 OIDC 왕복과 Sites assertion 발급 연동은 아직 수행하지 않았습니다.

로컬·운영 D1은 분리합니다. 기존 테이블을 유지하고 `0001_fearless_fenris.sql`로 `runtime_runs`, `0002_workflow_history.sql`로 발행 버전·댓글·감사 기록을 추가했습니다. 운영 배포·데이터 이관·부하·운영 D1 백업/복구·보존 정책 검증은 남아 있습니다. `.dev.vars`, `dist/server/.dev.vars`, `.wrangler/state`는 배포 자료나 소스 공유물에 넣지 않습니다.

## 확인한 결과와 남은 검증

- 현재 v5·로컬 운영 단계의 실제 OpenAI·MCP·외부 쓰기 API 호출은 0회입니다. 기존 키 조회·복사·생성·등록·사용 없이 모의 제공자와 합성 데이터를 사용했습니다. 이전 공개 MCP 읽기 검증 이력은 이번 호출과 별도로 관리합니다.
- 파일·OCR·예약·큐·평가·백업/복원은 실제 로컬 파일·프로세스와 내려받은 실행 프로젝트로 검사합니다. 모델·임베딩·웹 검색·원격 기억·보상은 모의 HTTP 계약과 미설정 차단 검사이며 실제 제공자 성공으로 표시하지 않습니다.
- 현재 31종 노드와 웹 발행·댓글·충돌·감사 기능의 검증 명령, 과거 통과 수, 화면 검증 상태는 [구현 기록](IMPLEMENTATION_PLAN.md)을 기준으로 합니다. 이번 입력 대기·AI 문서·등록 프로그램·작업 계약·P4 대표 경로의 최종 통합 결과는 [P1~P4 기록](P1_P4_IMPLEMENTATION.md)에 별도로 확정합니다.
- 기획 99개 전체나 P2~P4 모든 확장 기능이 완료된 것은 아닙니다. 임의 작업 생성·분산 점유·RAG 갱신/삭제/색인 전환·범용 코드 샌드박스·전체 DB 운영 등은 [범위 검토](P1_P4_SCOPE_REVIEW.md)에 남은 항목으로 구분합니다.
- 실계정 모델 → 도구 → 최종 답변, 실제 외부 쓰기·보상, 외부 SSO 왕복, 운영 배포·부하·장애 복구와 모바일 실기기 검증은 미완료입니다. 필요한 사용자 모델/서비스 자격 증명, 파일·OCR 의존성, 웹 OIDC/Sites·D1·배포 설정은 각 환경에서 구성해야 합니다.

Python 실행기의 HTTP 요청·응답에는 절대 마감 시간을 적용하고, 승인 남은 시간도 포함합니다. DNS/TLS 연결 단계는 운영체제의 시간 제한에 의존해 프로세스 반환이 늦어질 수 있으나, 연결 후 마감 시간이 지난 HTTP 요청 전송은 차단합니다. 운영체제 수준의 강제 종료를 보장하는 실행 격리는 제공하지 않습니다.

## 동적 Agent·지식 색인·후보 탐색

작업 조정의 동적 방식은 등록된 기능 틀과 입력 스키마를 사용한다. Python 다운로드에는 필요에 따라 `flowly_dynamic.py`가 포함된다. 지식 색인 관리에는 `flowly_knowledge.py`, ToT/GoT 후보 탐색에는 `flowly_search.py`가 포함되며 Node.js에서는 번들 안에 들어간다.

지식 세대는 실행 상태 폴더의 사용자·최상위 워크플로별 메모리에 저장된다. 모델 없이도 단어 검색의 준비·평가·발행·철회·복구를 실행할 수 있다. 벡터 모드는 `.env`의 `OPENAI_API_KEY`와 `FLOWLY_EMBEDDING_MODEL`을 사용하며 임베딩만 쓰는 흐름에는 `FLOWLY_MODEL`이 필요 없다. 검색과 평가는 대상 세대의 방식과 일치해야 한다. 현재 발행 세대만 조회할 수 있다.

후보 탐색은 현재 양의 정수 항목의 목표 합계 계약을 제공한다. 공개 후보·계보·검산·분기 상태를 저장하며 비공개 내부 사고는 요청하지 않는다. 설정·예제·검증과 남은 범위는 [후속 기록](DYNAMIC_RAG_SEARCH_IMPLEMENTATION.md)을 따른다.
