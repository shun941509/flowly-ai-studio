# 공개 후보 트리·그래프 탐색

2026-10-24 구현. `candidate_search`(후보 탐색) 블록으로 ToT의 부분 후보 확장·가지치기·되돌림과 GoT의 여러 부모 결합·계보·조상 변경에 따른 자손 무효화를 실행한다. 웹은 설계·내보내기만 제공하며 모델을 호출하지 않는다. Node.js·Python 실행기는 같은 설정과 상태 전이 계약을 사용한다.

## 이번에 구현한 문제 계약

입력은 `items: [{id,value}]`와 `target`이다. 항목은 중복 없는 1~20개 ID와 1~1,000,000의 양의 정수 값을 가지며, 목표는 1~10,000,000의 정수다. 후보는 원본에 있는 항목 ID들의 집합이다. 실행기가 원본 값으로 합계와 목표까지의 거리, 목표 충족 여부를 계산한다. 모델이 합계·점수·성공 여부를 지정하면 거절한다.

이는 검증기를 명확히 정의한 **항목 선택·합계 문제용 탐색 계약**이다. 임의의 기술·사업 문제의 정답을 판별하는 범용 평가기나 모든 경우를 탐색하는 완전 탐색은 아니다. 새 문제 종류에는 해당 입력과 후보를 실제로 검사할 결정적인 검증기 계약을 추가해야 한다. 같은 노드에 프롬프트만 변경해서 범용 문제 해결이 구현됐다고 표시하지 않는다.

## 트리 탐색

1. 빈 루트 `c0`에서 시작한다. 후보의 점수는 원래 목표와 합계의 절대 차이다.
2. 저장된 frontier를 거리, 깊이, 생성 순서로 정렬하여 다음 후보를 선택한다.
3. 모델은 선택된 부모의 항목을 모두 포함하는 새 자식을 제안한다. 부모를 임의로 바꾸거나 없는 항목을 추가할 수 없다.
4. 실행기가 직접 합계를 계산한다. 목표 초과 또는 깊이 한도에서 미완성인 후보는 막힌 가지가 된다. 너비 한도 밖의 후보는 가지치기한다.
5. 자식이 모두 막혔거나 제안이 없으면 기존 frontier의 다음 후보로 되돌아간다.
6. 검증한 해답, frontier 소진, 반복·후보 한도로 종료한다. 해답을 못 찾은 결과는 `solved:false`이며 해답이 존재하지 않는다는 증명이 아니다.

## 그래프 탐색

- 새 후보는 유효한 부모 1~3개를 연결하며 부모 항목의 합집합을 포함한다.
- 각 연결은 부모 ID와 당시 `revision`을 기록한다. 생성 순서가 위상 순서를 이루므로 사이클을 만들 수 없다.
- `revise`는 루트를 제외한 유효한 기존 후보의 항목을 수정한다. 부모 연결 변경은 허용하지 않는다.
- 조상 수정 시 모든 기존 자손을 `invalidated`로 변경한다. 수정한 조상의 새 버전으로 후속 후보를 새로 만든다. 무효화한 자손을 부모로 쓰면 거절한다.
- 한 모델 응답의 전체 작업 묶음을 복사한 상태에 검증·적용한다. 뒤 작업이 잘못되면 앞 작업의 조상 수정만 체크포인트에 저장되지 않는다.
- 단순 문자열 병합과 달리 후보 데이터·다중 부모·버전·무효화가 실제 실행 상태에 존재한다.

## 설정과 한도

| 설정 | 기본값 | 허용 범위 |
| --- | --- | --- |
| `mode` | `tree` | `tree`, `graph` |
| `itemsPath` / `targetPath` | `items` / `target` | 안전한 입력 필드 경로 |
| `maxDepth` | 4 | 1~8 |
| `maxCandidates` | 24 | 2~64, 루트 포함 |
| `maxIterations` | 12 | 1~32 |
| `branchFactor` | 3 | 1~6, 한 번의 모델 응답 작업 수 |
| `beamWidth` | 4 | 1~16, 유지할 frontier 수 |

외부 실행의 전체 모델 판단·토큰·시간·취소 한도도 동시에 적용한다. 탐색 반복 한도를 크게 설정해도 부모 실행 한도를 늘리지 않는다. 이 블록의 제안 Agent에는 도구를 허용하지 않으며 외부 쓰기를 수행하지 않는다.

## 체크포인트·관찰 기록

실행의 `searchStates[노드ID]`에 입력·설정 해시, 무결성 해시, 반복 번호, 후보, frontier, 부모 버전, 완료 상태와 공개 이벤트를 저장한다. 저장 순서는 요청 → 모델 응답 → 검증한 전체 상태 전이다. 모델 응답 저장 직후 프로세스가 종료되면 저장한 응답을 적용하고, 해당 응답을 얻기 위한 모델 요청을 다시 보내지 않는다. 모델 서비스가 응답했지만 응답 저장이 완료되기 전의 장애에서는 읽기 성격의 모델 요청이 재발생할 수 있다.

입력·설정·체크포인트 내용이 달라지면 재개하지 않는다. 완료한 탐색을 다시 `resume`해도 모델을 호출하지 않는다. 모델의 내부 사고 원문은 요구하거나 기록하지 않는다. 허용되지 않은 `reasoning` 등 응답 필드는 응답 체크포인트 저장 전에 거절한다. 기록은 후보 ID·항목·실제 계산값·부모 버전·생성/병합/무효화/가지치기/되돌림과 선택적인 짧은 공개 작업 설명이다.

## 대표 예제

| 대응표 | 실제 프로젝트 ID | 동작 차이 |
| --- | --- | --- |
| 097 | `p4-tree-candidate-backtracking` | 트리의 더 유망해 보인 막힌 가지에서 돌아가 형제 후보를 확장한다. 합계 검증 뒤 결과/보류로 분기한다. |
| 098 | `p4-graph-candidate-lineage` | 서로 다른 부모의 부분 후보를 결합하고 조상 변경 시 두 자손을 폐기한다. 새 버전으로 합성한 해답을 담당자 검토 대기·수락/거절로 연결한다. |

예제의 숫자는 합성 검증 자료다. 모델의 실제 문제 해결 정확도를 측정한 실계정 결과가 아니다. 사용자 모델의 제안이 계약에 어긋나면 실행이 실패하고, 후보가 소진되거나 한도를 사용하면 정답을 만들어내지 않고 보류한다.

## 사용자 설정

내보낸 ZIP의 `START_HERE.md`와 `README.md`를 따른다. `.env.example`을 `.env`로 복사한 뒤 사용자 기기에서 `OPENAI_API_KEY`와 `FLOWLY_MODEL`을 설정한다. 이 두 예제는 MCP를 사용하지 않아 MCP 주소·토큰이 필요하지 않다. Python ZIP에는 `flowly_search.py`가 포함되며 Node.js ZIP에는 같은 동작이 `runner.mjs`에 묶인다. API 키를 웹이나 워크플로 JSON에 넣지 않는다.

```powershell
node runner.mjs check
node runner.mjs run --input-file problem.json
# 또는
python runner.py check
python runner.py run --input-file problem.json
```

## 검증 증거와 경계

- `tests/search.test.ts`: 트리·그래프의 실제 상태, 가지치기·수치 초과·되돌림, 다중 부모와 새 버전 계보, 무효화, 응답 체크포인트 재개, 입력/설정/상태 변경 거절, 위조 후보·점수·성공 표시 거절, 취소, 두 언어의 출력·상태 완전 비교.
- `tests/test_export_search.py`: Python의 응답 저장 후 재개, 위조 응답, 잘못된 문제/한도, 취소·frontier 소진.
- `tests/search-export.test.ts`: 프로덕션 내보내기 생성기의 ZIP을 풀어 두 실제 CLI를 실행한다. 6개 사례 × 2개 언어를 검사하며, 첫 사례는 실제 프로세스를 저장 직후 종료 코드 86으로 끝낸 다음 잠금을 복구하고 같은 실행 ID로 재개한다. 모델 응답 횟수와 도구 호출 0회를 확인한다.
- 테스트의 모델 HTTP 응답만 명시적인 합성 응답으로 대체하고 그 밖의 네트워크는 차단한다. 검색·계산·상태 저장·프로세스 종료·재개는 실제 내보낸 코드가 수행한다. 실제 OpenAI·원격 MCP 호출 0회. 최종 전체 검사 수는 상위 단계별 구현·검증 문서와 현재 예제 검증 JSON을 따른다.
