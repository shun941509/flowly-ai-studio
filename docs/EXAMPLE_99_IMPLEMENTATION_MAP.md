# 99개 기획 예제와 현재 구현 대응표

기준일: 2026-10-24 · 범위: P0·P1~P4 및 동적 Agent·로컬 RAG 수명주기·후보 탐색 후속 구현

P0의 실제 변경·검증 결과는 [P0 내보내기 정합성 기록](P0_EXPORT_PARITY.md)을 따른다. P0 착수 분류는 구현됨 7·보강 필요 35·신규 개발 37·후순위 20이었다. 아래는 이번 실제 구현을 반영한 상태다. 공통 기본값·패키지 수정만으로 99개 예제의 상태를 일괄 상향하지 않는다.

이 문서의 `001`~`099`는 대화에서 합의한 **기획 예제 ID**다. 현재 `domain/workflow-designs/`의 **114개 개별 설계 ID와 다른 집합**이다. 비슷한 이름의 소스가 있더라도 목표 실행 흐름까지 구현됐다는 뜻이 아니다. 하나의 기존 설계를 여러 신규 예제의 완료 실적으로 중복 계산하지 않는다.

이 문서는 구현 출발점을 보존한다. 이후 단계가 완료되면 해당 행의 상태·검증 증거·변경일을 함께 갱신한다. 기존 3,200개 확장 목표나 그 완료 판정을 99개 기획의 완료 판정과 섞지 않는다.

## 분류와 증거의 범위

| 분류 | 수 | 기준 |
| --- | ---: | --- |
| 구현됨 | 17 | 기획의 핵심 제어 흐름이 소스에 있고 두 언어의 CLI 검증 기록이 있다. 실제 모델의 답변 품질이나 사내 서비스 연결 완료를 뜻하지 않는다. |
| 보강 필요 | 35 | 직접 재사용할 핵심 흐름 또는 실행 기반이 있으나 기획에 필요한 행동·상태·검증이 부족하다. |
| 신규 개발 | 32 | 일반 노드를 조합할 기반은 있지만 해당 업무 계약과 핵심 실행 행동을 새로 구현해야 한다. |
| 후순위 | 15 | 아직 완료되지 않았다. 선행 기능 또는 운영·복구 계약이 필요하므로 뒤 단계에서 구현한다. 제외 항목이 아니다. |
| 합계 | 99 | 모든 기획 ID는 한 번만 분류한다. |

분류는 **핵심 워크플로 기준**이다. AI 명령 프롬프트·`AGENTS.md`·Skill 패키지 생성은 P0 착수 시점에 공통 미구현 항목이었으며 이번 P1에서 구현했다. 이 공통 내보내기의 추가가 아직 없는 예제의 업무 동작을 자동으로 구현하지는 않는다.

착수 시 기존 증거인 `examples/workflow-verification.json`에는 소스 카탈로그 102개, 두 언어 ZIP 204개, 검사 1,328건, 실패 0건, 외부 호출 0회가 기록되어 있다. 이 수치는 **이 문서를 작성하면서 새로 실행한 검사 수가 아니다**. 런타임·생성기·시나리오가 바뀌면 현재 소스의 증거를 다시 생성해야 한다. 실제 ZIP 프로세스와 데이터·제어 흐름을 실행하되 모델·임베딩·MCP 경계에 테스트 응답을 주입하는 검증이다. 실계정 연동·모델 정답률의 증거로 사용하지 않는다.

## 2026-10-24 변경 증거와 남은 범위

004·007·019·023·099의 핵심 흐름을 추가했다. 091·092·094는 등록 도구 계약을 통한 대표 경로를 구현했지만 전체 기획이 남아 `보강 필요`로 분류한다. 013·093의 의존 관계·완료 조건 공통 기반은 보강했으며 동일 통합 예제를 여러 완성 프로젝트로 세지 않는다. 신규 공개 그래프 6개는 체크포인트 1·데이터 검증 3·통합 2다.

후속 단계에서 031·052·059·097·098의 핵심 계약을 구현했고, 053은 로컬 철회 경로를 구현하여 신규 개발에서 보강 필요로 옮겼다. 추가된 실제 독립 그래프는 6개다. 구체적 범위와 현재 검증은 [동적 Agent·RAG·후보 탐색 기록](DYNAMIC_RAG_SEARCH_IMPLEMENTATION.md)을 따른다.

이전 단계의 전체 실행 증거는 [P1~P4 변경·검증 기록](P1_P4_IMPLEMENTATION.md)과 `examples/workflow-verification.json`을 따른다. [범위 검토](P1_P4_SCOPE_REVIEW.md)는 후속 변경과 여전히 남은 분산 점유·실패 재배정·외부 지식 서비스 기능을 구분한다. `tests/export-checkpoint-restart.test.ts`는 카탈로그 시나리오와 별도로 두 실제 프로세스의 강제 종료·복구를 검증한다. 실제 서비스 호출은 0회이며 실모델 품질·사내 MCP 연동은 미검증이다.

## 공통 내보내기 계약

하나의 검증된 실행 manifest를 기준으로 Node.js·Python과 AI 작업 문서를 생성한다. 문서용 그래프와 실행용 그래프를 따로 관리하지 않는다. `workflow.json`의 버전·변환·검증을 유지하고, 두 실행기가 같은 기본값과 오류·분기·재개 의미를 사용하게 한다.

| 산출물 | 생성 내용·역할 | 착수 시점 / 계획 |
| --- | --- | --- |
| `workflow.json` | 노드·연결·매핑·자료 스냅샷·허용 도구·한도·승인 정책·버전 | 기존 구현 재사용; P0 기본값과 경로 정합성 |
| Node.js `runner.mjs` | 같은 manifest를 실행하는 실제 CLI | 기존 구현 재사용; P0 오류 수정·동일 시나리오 회귀 |
| Python `runner.py` | 같은 manifest를 실행하는 실제 CLI | 기존 구현 재사용; P0 기본값·분기·재개 동등성 |
| 파일·트리거·운영 도우미 | 필요한 파일 처리, 지속 트리거, 운영 CLI/로컬 화면, 의존성 안내 | 편집기에는 전달되지만 직접 예제 경로에 누락된 P0 착수 격차 수정 |
| `AI_PROMPT.md` | 목표, 읽을 파일 순서, 시작 입력, 성공 조건, 중단·보고 규칙 | P1 구현 · 2026-10-24 |
| `AGENTS.md` | 프로젝트 범위, 역할 계약, 도구·자료 범위, 승인·실패·재개 규칙 | P1 구현 · 2026-10-24 |
| `skills/<id>/SKILL.md` | 선택된 Skill의 작업 절차·입출력·필요 도구·완료 기준 | P1 구현 · 2026-10-24. Skill 원문이 실행 정책을 바꿀 수 없음 |
| `START_HERE.md` | 사용 순서, AI 작업 문서와 실행기 차이, 지원 기능·미설정 상태 | P1 구현 · 2026-10-24 |
| 예제 계약·시나리오 | 입력·기대 결과·분기·실패·재개 수용 기준 | 기존 `example-contract.json`, `input.txt`, `EXAMPLE.md` 활용; 기대 결과와 실제 결과 구별 |
| `README.md`, `.env.example`, `.gitignore` | 정확한 실행·설정 위치·명령·제약 | 기존 구현 보강; 빈 비밀 설정만 포함 |

일부 AI 도구는 `AGENTS.md`나 Skill을 자동으로 읽지 않는다. 시작 프롬프트가 필요한 파일을 읽는 순서를 안내한다. Markdown 지침 자체가 병렬 실행·권한·승인·복구를 강제하지 않으므로, 실제 실행의 제어와 증거는 실행기·등록 도구가 담당한다.

웹은 OpenAI 호출·키 등록을 제공하지 않는다. 사용자는 내보낸 폴더에서 `.env.example`을 `.env`로 복사하고 모델을 사용하는 경우 `OPENAI_API_KEY`, `FLOWLY_MODEL`을 직접 설정한다. MCP는 ‘도구 및 자료’에 등록한 정의를 내보내고, 정확한 `FLOWLY_MCP_ENDPOINT_…`·`FLOWLY_MCP_TOKEN_…` 이름과 필요 도구 계약을 ZIP의 안내에 표시한다. 비밀 값은 ZIP·워크플로 JSON·로그·Git에 포함하지 않는다. 회사 네트워크가 접근·통신 범위를 관리하므로 별도 사내 주소 허용 목록을 새로 만들지 않는다.

Node.js의 기본 AI/데이터 실행과 Python 도우미를 사용하는 파일·트리거·운영 기능의 의존성을 구별한다. 필요한 Python·라이브러리·OCR 구성 요소가 없으면 해당 기능을 `미설정`으로 표시한다. 테스트 응답을 제품 ZIP에 넣거나 미설정을 성공 결과로 바꾸지 않는다.

## P0부터의 구현 순서와 완료 기준

### P0 — 대응표·기본값·패키지 정합성

착수 시 구체적으로 확인한 격차:

- `maxRounds`가 생략된 적응형 작업 조정에서 Node 엔진은 `1`, Python 실행기와 UI는 `3`을 사용한다. 명시된 값은 보존하고, 생략값·경계값·직접 manifest/편집기 정의 모두에서 같은 의미가 되게 수정한다. 오래된 JSON의 해석이 달라지는 범위는 기록한다.
- 편집기 내보내기는 파일·트리거·운영 소스를 전달하지만 `buildExampleExport()`는 실행기 소스만 전달한다. 파일 처리가 필요한 예제의 직접 다운로드는 필수 도우미 누락으로 실패할 수 있다. 기존 102개가 전부 고장났다는 뜻은 아니다. 두 경로의 공통 구성과 필요한 파일 포함 규칙을 일치시킨다.
- 현재 99개와 소스 102개의 대응이 문서화되어 있지 않다. 이 표를 기준선으로 삼고 현재 증거와 미래 목표를 분리한다.

수용 기준:

1. 001~099가 누락·중복 없이 존재하고 7/35/37/20 기준선과 일치한다. 관련 소스가 기획 전체를 구현하지 않았으면 그 차이를 표시한다.
2. 같은 입력·생략된 기본값·명시값·잘못된 값에서 Node.js/Python의 선택 작업, 라운드 수, 결과와 오류가 일치한다. 기본값 차이를 재현하는 회귀 검사가 먼저 존재해야 한다.
3. 직접 예제 ZIP과 편집기 ZIP의 지원 기능에 필요한 실행 파일·도우미·설정 안내가 누락되지 않는다. ZIP 내용 확인만으로 끝내지 않고 두 언어 CLI에서 필요한 기능을 실행한다.
4. 웹 `live` 요청·이전 큐 처리·내보내기에서 모델 호출이 발생하지 않는다. 미설정 시 명확히 중단한다.
5. 관련 타입 검사·회귀 검사를 현재 소스로 수행하고, 오래된 ZIP/지문의 통과 기록을 새 결과로 재사용하지 않는다. API 키 조회·등록 및 실제 서비스 호출 없이 검증한다.

### P1 — 대표 흐름과 AI 작업 문서 패키지

001~006과 017·022의 기존 계약을 재사용하고 004의 보완 입력·지속 재개, 023의 중단·복구 예제를 우선 완성한다. 같은 manifest에서 AI 프롬프트·AGENTS·Skill·시작 안내를 생성한다.

수용 기준: 정상·필수 근거 누락·형식 오류·한도 초과·검토/승인 거절·재시작·불명확한 쓰기 결과를 양쪽 실제 CLI에서 검사한다. 동일 실행 ID의 재개와 완료한 단계 보존을 확인하고, 승인 전 쓰기 0회·정확한 승인 후 1회·거절 후 0회를 테스트 경계에서 검증한다. 문서가 실제 지원하지 않는 행동을 약속하지 않게 manifest와 대조한다.

### P2 — 데이터·검색·독립 검증

등록된 결정적 계산·검증 계약, 검색 결합·근거 대조, 스키마 오류의 정확한 수정, 구조화된 보완 입력을 먼저 추가한다. 007~010·013·015~016·018~021·024~027·030·033~035·039·055~056·058·096 기초·099를 그 기반으로 완성한다.

수용 기준: 입력이 달라지면 실제 다음 노드의 입력·조건·계산·근거가 달라진다. 모델이 계산·검증 성공을 말한 것만으로 통과하지 않는다. 자료 없음·충돌·단위 불일치·필드 오류를 각각 검사한다. 099의 독립 검증 단계에 초안이나 초안의 결론이 새어 들어가지 않는지 확인한다.

### P3 — 지속 상태·동적 작업·전문 어댑터

작업 계약·생성/점유·의존성·무효화·재개를 공통 상태로 구현한 뒤 동적 Sub-agent·재계획·장기 업무를 연결한다. RAG 청크 갱신·삭제·색인 세대와 근거 계보를 추가한다. 코드·DB는 등록된 프로그램/사내 MCP 계약과 격리된 테스트 어댑터부터 구현한다. 093의 독립 완료 조건 평가를 먼저 검증한다.

수용 기준: 중단/재시작 후 작업 소유권·부모 예산·완료 결과가 유지된다. 재계획이 완료한 외부 쓰기를 다시 실행하지 않는다. 자료·목표·코드 버전 변경 시 영향받는 결과만 무효화한다. 테스트용 로컬 DB·합성 문서·임시 코드 작업 공간에서 읽기·변경 계획·시험 결과를 실제 계산하며, 아직 없는 실서비스 연결은 `미설정`으로 표시한다.

### P4 — 운영 변경·복잡한 탐색·최상위 통합

개별 코드 실행 기능 → 046 개발팀 → 077 지식 관리 → 078 근거 기반 개발 → 091 DB 통합 → 092 코드·DB 변경 → 094 목표 기반 통합 순으로 의존성을 충족한다. 093 완료 조건 오케스트레이션을 재사용한다. ToT/GoT의 지속 후보 탐색과 정수 합계 검증은 이번 후속 단계에서 구현했다. 다른 업무 문제의 검증기, 아바타·복잡한 코드/DB 기능은 필요한 지속 상태·도구를 추가해 확장한다. 095의 전체 블록 검증은 P0에서 기반을 만들고 이 단계까지 계속 확장한다.

수용 기준: 선택된 팀·단계가 실제 산출물을 다음 단계로 전달하며 독립 완료 평가를 통과한다. 시험 DB의 승인된 변경·실패·불명확한 결과·복구를 두 언어에서 검사한다. 복구가 원래 성공한 부작용을 중복 실행하지 않는다. 전체 블록은 의미 있는 성공/실패/건너뜀/재개 시나리오로 검증하며 억지로 모든 블록을 한 경로에 나열하지 않는다.

## 단계별 완료 보고

각 단계는 다음을 함께 기록한다.

- 구현한 기획 ID와 기존 소스 ID, 변경한 사용자 동작, 남은 격차.
- 실제 실행한 명령·시나리오·결과·현재 실행기/ZIP 증거. 수행하지 않은 검사를 통과로 표시하지 않음.
- 외부 OpenAI·MCP 호출 수. 이 계획의 개발 검증은 실제 서비스 호출 없이 수행하며, 테스트 경계와 실제 로컬 파일/DB/프로세스 실행을 구별.
- 사용자 설정 위치와 필요한 런타임·선택 의존성. 모델 품질·사내 MCP 호환성·실제 SSO·운영 부하 검증이 남으면 별도 표시.

기존 `pnpm catalog:complete`는 3,200개 목표를 검사한다. 이를 그대로 99개 기획의 완료 명령으로 사용하지 않는다. 99개는 이 대응표의 상태와 각 목표 계약·현재 두 언어 증거로 별도 판정하고, 3,200개 확장 목표는 기존 집계에 독립적으로 남긴다.
