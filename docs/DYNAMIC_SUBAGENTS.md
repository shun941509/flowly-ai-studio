# 실행 중 하위 Agent 생성

2026-10-24. 기존 작업 조정 노드의 `mode: "dynamic"`으로 제공한다. 새 노드를 같은 뜻으로 중복 추가하지 않는다. 웹은 기능 계약을 편집·검사·내보내고 OpenAI를 호출하지 않는다.

## 생성 범위

기존 `tasks`는 사용자가 등록한 **기능 템플릿**이다. `dynamic.templates`는 각 기능의 Agent 블록과 생성 입력의 객체 스키마를 지정한다. 모델은 해당 기능에서 새 역할·목표·입력·작업 ID·선행 관계를 생성한다. 동일 기능에서 서로 다른 역할의 독립 실행을 여러 개 만들 수 있다. 기존 계획 방식처럼 등록된 작업 ID 목록만 선택하는 동작과 구분한다.

```json
{
  "mode": "dynamic",
  "maxTasks": 1,
  "tasks": [{ "id": "analysis", "name": "분석 기능", "definition": "등록된 실제 하위 그래프" }],
  "dynamic": {
    "maxAgents": 4,
    "concurrency": 2,
    "templates": [{
      "taskId": "analysis",
      "agentNodeId": "specialist",
      "inputSchema": {
        "type": "object",
        "properties": { "topic": { "type": "string" } },
        "required": ["topic"],
        "additionalProperties": false
      }
    }]
  },
  "completion": [{ "path": "summary.completedCount", "operator": "gte", "value": 2 }]
}
```

위 예시는 필드 안내다. `definition`에는 실제 하위 그래프 객체가 필요하다. `maxTasks`는 이전 문서 계약을 유지하는 설정이며, 동적 모드의 실제 생성 수 제한은 `maxAgents`다.

모델의 계획은 다음 형식만 허용한다. 추가 `tools`, `code`, `limits`, `policy` 같은 필드는 거절한다. `input`은 등록한 스키마로 검사한다. 생성 ID는 영문 또는 밑줄로 시작하는 영문·숫자·밑줄 40자 이내다. 역할 80자·목표 2,000자·전체 계획 20,000자 한도를 둔다.

```json
{
  "agents": [
    { "id": "performance", "templateId": "analysis", "role": "성능 분석", "goal": "병목과 근거를 보고", "input": { "topic": "응답 지연" }, "dependsOn": [] },
    { "id": "judge", "templateId": "analysis", "role": "독립 판단", "goal": "앞선 분석의 충분성을 확인", "input": { "topic": "최종 판단" }, "dependsOn": ["performance"] }
  ]
}
```

기능 그래프·자료·허용 도구·승인 정책은 기존 등록값을 복사한다. 지정된 Agent의 지침에 역할과 목표를 추가할 뿐 임의 코드·새 MCP·권한을 만들지 못한다. 기존 지침과 생성 지침의 합계가 12,000자를 넘으면 조용히 자르지 않고 실패한다. 기능 안에 동적 생성을 다시 중첩할 수 없다.

## 실행·대기·재개

1. 부모의 남은 모델·도구·토큰·시간 예산으로 계획을 만든다.
2. 등록 기능·스키마·생성 수·중복 ID·없는 선행 작업·의존 순환을 검사한다.
3. 생성 계획, 설정 해시, 원래 입력 해시, 계획 해시를 자식 실행 전에 지속 저장한다.
4. 자식마다 별도 실행 ID·정의 해시·입력 해시·선행 ID·상태를 기록하고 부모 예산을 분할한다.
5. 선행 결과가 완료된 역할만 실행한다. 최대 생성 수는 8, 동시 실행은 4 이내다. 실제 설정이 더 작으면 그 값을 따른다.
6. 자식의 추가 입력·사람 검토·도구 승인은 기존 절차대로 기다린다. 제출·결정은 저장만 하며 명시적인 `resume`이 실행을 이어간다.
7. 저장된 계획·정의·입력 계약을 확인하고 같은 자식 실행 ID로 이어간다. 완료한 역할이나 계획을 다시 실행하지 않는다.
8. `{input, artifacts, summary}`에 대한 등록 완료 조건을 별도로 검사한다. `artifacts.생성ID`는 실제 완료 출력이며, `summary.agentCount`와 `summary.completedCount`는 엔진이 계산한다.

동적 생성을 사용하는 워크플로는 전체 실행 블록도 보수적으로 120개까지 제한한다. 각 생성 수뿐 아니라 같은 그래프의 다른 조정 노드, 바깥 반복 횟수, 적응형 조정의 작업 수·라운드 수를 모두 곱하거나 더해 검사한다. 실제 분기가 적게 실행될 예정이어도 설정된 최대치가 한도를 넘으면 다운로드 전에 줄여야 한다. 동적 생성을 사용하지 않는 기존 문서에는 이 새 확장 검사로 호환성 변경을 만들지 않는다.

자식 시작 입력은 `{text, assignment:{id,role,goal,input}, artifacts}`이다. `artifacts`에는 해당 역할의 `dependsOn`으로 선언한 완료 출력만 들어간다. Agent 블록까지 명시적 입력 매핑을 연결해야 한다. 기능의 기존 노드 입력·출력 스키마 검사는 그대로 적용된다.

이번 동작은 조정 노드에 도달했을 때 **한 번 생성한 계획**의 지속 실행이다. 진행 중 기능 코드를 바꾸거나 무제한 재귀 생성·분산 소유권 임대·새 서비스 자동 등록을 제공하지 않는다. 자료 권한은 기존 실행 경계에서 검사하며, 내보낸 자료 사본에 이후 웹의 공유 철회를 원격 전파하지는 않는다.

## 대표 예제와 검증

`dynamic-subagent-task-team`은 하나의 등록 분석 기능에서 요청에 따라 2개 또는 3개 역할을 생성한다. 두 분석은 병렬로 실행하고, 판단 역할은 두 산출물이 준비된 뒤 시작한다. 보완이 필요한 역할만 입력을 기다리며 다른 완료 결과를 보존한다. 생성된 판단 결과가 독립 완료 조건을 통과한 경우만 최종 출력한다.

- `tests/dynamic-agents.test.ts`: 실제 엔진의 병렬 선행 작업·계획 선저장·타입 계약·권한 필드 거절·예산·완료 조건·동일 실행 보완 입력·승인/거절/재개·기록 변조·지침 길이 경계를 검사한다.
- `tests/test_export_dynamic.py`: Python의 같은 계약과 잠금 아래 자료 버전 비교·교환을 검사한다.
- `tests/dynamic-export.test.ts`: 생산용 ZIP을 만들고 두 실제 CLI를 실행한다. 서로 다른 생성 수·노드 경로·보완 입력·실패 계획 등 9개 시나리오를 언어별로 검사한다. AI 작업 문서도 같은 manifest에서 내보낸다.

검증의 모델 응답은 ZIP 밖의 테스트 경계에서 제공하고 다른 네트워크를 차단한다. 실제 OpenAI·원격 MCP 호출은 0회다. 사용자는 내보낸 `START_HERE.md`에 따라 `.env`에 자신의 모델 설정과 필요한 사내 MCP 연결을 넣는다. 테스트 응답·가짜 키·개발 경계 스크립트를 제품 ZIP에 포함하지 않는다. 실모델의 역할 선정 품질과 회사 서비스 연결 성공은 별도 검증 범위다.
