# 등록 작업 의존 관계와 완료 조건

P3의 이번 구현은 작업 조정 노드가 **등록된 하위 작업**을 선택하는 실행 계약을 보강한다. 모델이 임의의 새 코드·도구·Agent 정의를 생성해 실행하는 기능은 아니다. 웹은 설계와 내보내기를 담당하며 OpenAI를 호출하지 않는다.

후속 `mode=dynamic`은 등록된 Agent 작업 틀에서 새 역할·목표·입력·선행 계약을 생성합니다. 일반 등록 작업 방식과 구별하며 [동적 생성 계약](DYNAMIC_SUBAGENTS.md) 및 [후속 구현 기록](DYNAMIC_RAG_SEARCH_IMPLEMENTATION.md)을 따릅니다. 아래 설명의 임의 생성 미지원은 기존 plan/adaptive 방식의 경계입니다.

## 설정

`orchestration.tasks[].dependsOn`에는 같은 조정 노드에 등록한 작업 ID를 넣는다. 없는 ID·중복·순환 의존 관계는 설계 검사에서 거절한다. 모델의 계획은 선행 작업을 이미 완료했거나 같은 계획에서 먼저 선택해야 한다. 실행 순서는 현재 조정 노드의 순차 작업 규칙을 유지한다.

`orchestration.completion`에는 기존 조건 비교 형식의 조건을 1~20개 등록한다. 비교 대상은 `{input, artifacts}`이며 `artifacts.작업ID`는 그 작업에서 마지막으로 완료한 실제 출력이다. 예를 들어 `artifacts.tests.data.passed`가 `true`인지 검사할 수 있다. 누락된 값·맞지 않는 자료형은 통과로 처리하지 않는다.

```json
{
  "mode": "adaptive",
  "maxRounds": 3,
  "maxTasks": 2,
  "tasks": [
    { "id": "research", "name": "조사", "definition": "별도 하위 그래프 객체" },
    { "id": "verify", "name": "검증", "dependsOn": ["research"], "definition": "별도 하위 그래프 객체" }
  ],
  "completion": [{ "path": "artifacts.verify.data.passed", "operator": "eq", "value": true }]
}
```

위 예시는 필드 설명용이다. `definition` 자리에는 실제 하위 그래프 객체가 필요하다. 입력·결과 스키마와 연결은 편집기에서 정의한다.

의존 관계나 완료 조건을 설정한 작업의 최초 입력에는 원래 입력과 `artifacts` 객체가 전달된다. `artifacts`에는 그 작업이 `dependsOn`으로 선언한 선행 작업 출력만 들어간다. 예전 정의에 새 설정이 없으면 기존 적응형 작업의 `results`·`round` 전달을 유지한다.

## 실행·중단·재개

각 하위 실행에 작업 ID·정의 해시·입력 해시·선행 작업 ID·하위 실행 ID·상태를 기록한다. 재개와 작업 시작 전에 정의와 입력을 검사한다. 완료된 단계는 그대로 보존하며, 추가 입력은 별도의 입력 요청에 저장한 뒤 `resume`으로 이어간다.

적응형 조정에서 모델이 완료를 선언해도 등록된 완료 조건을 별도로 검사한다. 실패하면 검사 결과를 저장하고 남은 라운드 안에서 다시 계획한다. 최대 라운드에 도달하면 `budget_exceeded`로 끝난다. 한 번만 계획하는 방식에서는 미충족 완료 조건이 실행 실패이며, 설정한 오류 분기가 있으면 그 경로로 전달한다.

새 계약을 사용하는 같은 작업의 정의·입력이 동일하면 완료된 출력을 재사용하고 원래 실행 ID를 `task_reused` 이벤트에 기록한다. 모델·도구 사용량을 다시 더하지 않는다. 이미 완료한 외부 쓰기를 다른 입력으로 다시 계획하면 실행을 중지한다. 결과가 불명확한 외부 쓰기는 기존 원장 규칙에 따라 자동 재실행하지 않는다.

완료 조건이 실패해 수정이 필요하면 기존 결과를 입력으로 받는 **별도 수정 작업**과 검증 작업을 등록한다. 같은 입력의 완료 작업을 반복 선택하는 것은 새 실행 요청이 아니다. 자동 의존 결과 무효화·임의 하위 Agent 생성·새 업무 목표 자동 수립은 이번 구현에 포함하지 않는다.

## 로컬 검증

- `tests/orchestration-contracts.test.ts`: 선행 출력 전달, 잘못된 계획/순환, 독립 완료 검사, 계약 변조 후 재개 거절, 승인된 쓰기 결과 재사용.
- `tests/test_export_contracts.py`: 동일한 Python 엔진 계약과 다른 입력으로 재계획한 쓰기 차단.
- `tests/export-task-contracts.test.ts`: 실제 두 언어 ZIP의 CLI를 실행하여 의존 관계·완료 판단·라운드 한도·결과 재사용·중첩 추가 입력/재개 12개 조합 검사.

CLI 검사의 모델 응답은 ZIP 밖의 명시적인 테스트 경계에서 주입하며 그 밖의 네트워크를 차단한다. 제품 ZIP에 테스트 응답을 넣지 않는다. 실제 OpenAI·MCP 서비스 호출과 모델의 업무 정답률은 이 검증에 포함하지 않는다. 사용자는 내보낸 `.env.example`을 `.env`로 복사한 뒤 해당 환경에서 모델과 사내 MCP 연결 값을 설정한다.
